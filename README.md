- S3 compatible storage

# How To Build
- Sync the repository
- Open GenServices.sln
- Build the solution for x64, Windows (or your architecture & OS if different)
- Edit appsettings.json and fill out any TODO sections (e.g. token settings, database settings)
- Choose the database in the `Database` section of appsettings.json:
  - `db_provider` is `"postgres"` (PostgreSQL, the default when the key is missing or empty) or `"mysql"` (MySQL/MariaDB, `"mariadb"` is accepted too). Any other value stops the service at startup
  - Create an empty database and a user with full access to it, then fill in `db_host`, `db_port` (5432 for PostgreSQL and 3306 for MySQL/MariaDB when missing), `db_name`, `db_username` and `db_password`
  - PostgreSQL only: `db_host` may list several servers (`"10.66.0.1,10.66.0.2"`); set `db_target_session_attributes` to `"primary"` so the service always connects to the writable one, also after a failover. With `"mysql"` the setting must stay empty, the service stops at startup otherwise
  - New installs should use PostgreSQL
- Create the database schema by running `GenOnlineService migrate` (there is no SQL to import)
- Run GenOnlineService.exe. The service never changes the schema itself and refuses to start while migrations are pending
- `Core:enforce_https` is one switch, `true` when missing: sign-in requires https (the accounts server refuses plain http requests and its cookies are https-only), http requests are redirected to https when the service knows its https port (`ASPNETCORE_HTTPS_PORT` or an https endpoint; an http-only container behind a TLS proxy relies on the proxy for that), and responses over https send HSTS except to localhost. Behind a TLS-terminating proxy list it in `TrustedProxies` so the forwarded scheme counts as https. A local run over plain http (no TLS in front, for example `http://127.0.0.1:5000`) must set it to `false` explicitly, with `"Core": { "enforce_https": false }` in appsettings.json or the environment variable `Core__enforce_https=false`; `false` turns off all of these at once. Keep it `true` wherever the service is reachable from other machines
- When upgrading, stop the service, run `GenOnlineService migrate --yes`, then start the new version. With multiple instances, the old instances may keep running during the migration only if it is backward compatible, then roll the instances

# Running The Tests
- `dotnet test GenOnlineService.Tests/GenOnlineService.Tests.csproj -p:Platform=x64` runs the unit tests. The database probe tests are skipped unless at least one probe server is set
- Each probe variable holds a server connection string without a database name; every probe test creates its own database on that server and drops it afterwards. Set any combination:
  - `GENONLINE_PROBE_POSTGRES`: PostgreSQL, for example `Host=127.0.0.1;Port=5432;Username=postgres;Password=<password>`
  - `GENONLINE_PROBE_MARIADB`: MariaDB, for example `Server=127.0.0.1;Port=3306;User=root;Password=<password>`
  - `GENONLINE_PROBE_MYSQL`: MySQL 8.4, for example `Server=127.0.0.1;Port=3307;User=root;Password=<password>`. MySQL and MariaDB use the same `mysql` provider but differ (for example `json` columns are real JSON on MySQL and text on MariaDB), so run both before changing MySQL/MariaDB queries
- CI sets `GENONLINE_PROBE_POSTGRES` and `GENONLINE_PROBE_MARIADB`

# Releases
- Releases are tags on `main` using semantic versioning. The service is in alpha: versions are `0.x`, and a minor version (`0.2` to `0.3`) may contain breaking changes to the client protocol, the configuration or the schema; patch versions only contain fixes
- A `vX.Y.Z` tag (only plain tags count as versions; any other tag is ignored) builds the linux-x64 artifact (`genonlineservice-<version>-linux-x64.tar.gz` plus its SHA-256, attached to the GitHub release, marked as a pre-release while in `0.x`) and the container image `ghcr.io/<owner>/genonlineservice:<version>` (also tagged with the 8-character commit). `latest` points at the newest release; deployments should still pin an exact version or commit
- The git tag is the only source of the version (the project file has none) and `GET /-/health` reports it: `0.1.0+<8-character commit>` on the tag `v0.1.0`, `0.1.0+20.<commit>` 20 commits after it, `0.0.0+<commit>` when no `v*` tag is reachable
- The build always computes it from git (an MSBuild target running `git describe`, there is no override), so it needs the tags and the `.git` directory: CI checks out with `fetch-depth: 0` (and fails a build whose version does not match the commit or tag) and the Docker build copies `.git` into the build stage; a build without git reports `0.0.0+unknown`. In a git worktree `.git` only points into the main repository, so build the image with `scripts/docker-build.sh`, which passes that repository as the `git` build context; a plain `docker build` there stops with that hint. Sentry's release uses the same string. The build also writes it to `version.txt` in the publish output, which CI reads to name the artifact: `genonlineservice-<X.Y.Z>-linux-x64.tar.gz` for tags, the commit otherwise; image tags cannot contain `+`, so they stay the semver tag, the commit, and `main`

# Running The Image
- The image ships no `appsettings.json` (the sample binds `localhost` with HTTPS, which has no certificate in a container). Mount your own at `/app/appsettings.json` and mount `data/`, `crcfiles/` and `Exceptions/` (`/app/data`, `/app/crcfiles`, `/app/Exceptions`). The container runs as a non-root user, so they must be writable by it, and a mounted `data/` replaces the shipped one: start it from a copy of `GenOnlineService/data`
- Either leave the `Kestrel` section out of that file, so the image listens on `http://0.0.0.0:8080` (`ASPNETCORE_HTTP_PORTS`), or define a single HTTP endpoint on `0.0.0.0:8080`. Terminate TLS in front of the container
- Apply the schema with the same mounts: `docker run --rm -v ./appsettings.json:/app/appsettings.json:ro ghcr.io/<owner>/genonlineservice:<version> migrate --yes`

# Importing The Old Production Database
The schema is v1 (`docs/schema.md`): every environment has its own database, and the old production MariaDB is converted once into the prod environment. `GenOnlineService import [--dry-run] [--yes]` reads the database in the `Import` section (`db_provider` `mariadb` or `mysql`, `db_host`, `db_port`, `db_ssl_mode`, `db_name`, `db_username`, `db_password`) and writes into the database in the `Database` section (PostgreSQL or MySQL/MariaDB). The source is only read, inside one consistent snapshot.
- Create an empty target database and run `GenOnlineService migrate --yes` against it. The import refuses a target with pending migrations or with any rows
- Validate: the import first reads everything and writes nothing. It prints the users that are dropped (`Ghost` and `DevAccount` accounts: their match slots stay with no user), the staff remap report (every user with `admin` or `permissionslevel`, which are not imported: grant roles again with `roles grant`) and the findings that block the import: `duplicate_identities`, `duplicate_emails`, `username_collisions`, `invalid_usernames`, `orphaned_rows`, `invalid_values`, `invalid_json`. Resolve them in the source, or waive them in `Import:waive` (a list of those names). A waived duplicate stays with the user who signed in last; a waived username collision (an equal name after NFKC and upper case, or a look-alike under the name key) gets `<name>_<id>`, a waived invalid name (empty, too long, a NUL, or leading or trailing whitespace) gets `player_<id>`; waived orphans and invalid rows are left out or lose their user
- Convert: one transaction on the target, table by table. Legacy bans become local `ban` sanctions with an `audit_log` entry (`Import:legacy_bans` `local`, the default, or `skip`). Device values are stored as HMAC-SHA-256 with the key at `Devices:hmac_key_path` (`data/device_hmac.key` by default), created when missing: back it up with the database and give the service the same key. Every user is imported as `active`; the old `users.active` column is ignored. Old statistics (`daily_stats`, `service_stats`, `connection_outcomes`) are not imported
- Verify: every target table is read back and compared with what was written (row counts and SHA-256 row checksums), and the identity sequences are checked to continue after the highest imported id. Only then does the transaction commit; `--dry-run` rolls it back instead
- The report is printed and written to `Import:report_path` (`import-report-<time>.txt` by default). Exit code 2 means blocking findings, 1 a failure (nothing was written)
- Imported players sign in with the Discord, Steam, Google or GameReplays account linked in the old database: the import writes those links to `identities` under the provider names `steam`, `discord`, `google` and `gamereplays`, and the first sign-in through the provider of that name lands on the imported user, name and tag included. `Import:keycloak_file` is gone; a config that still sets it stops the import
- Cutover: stop the old service, run the import, start the new deploy. Devices whose user last signed in more than 180 days ago are removed by the first retention purge

# Changing The Database Schema
The schema is defined by the EF Core model (`GenOnlineService\Database`) and applied through code-first migrations. Migrations are only applied by `GenOnlineService migrate`, never by the service itself.

The model is shared, but every provider has its own context (`MySqlAppDbContext`, `PostgresAppDbContext`) and its own migrations (`GenOnlineService\Database\Migrations\MySql` and `...\Postgres`). **Every model change needs a migration for both contexts.** The conventions and portability rules are in `docs/schema.md`: no unsigned types, UTC timestamps (`datetime(6)` / `timestamptz`), JSON as `json` / `jsonb`, uniqueness through `*_normalized` columns. Provider specific column types belong in the derived contexts (`Database.Providers.cs`), not in the shared configuration classes. Raw SQL statements need a branch for both providers. Do not write SQL outside generated migrations.
- Restore the local tools once: `dotnet tool restore`
- After changing the model, create the migrations from the `GenOnlineService` folder:
  - `dotnet ef migrations add <Name> --context MySqlAppDbContext -o Database/Migrations/MySql -n GenOnlineService.Migrations.MySql`
  - `dotnet ef migrations add <Name> --context PostgresAppDbContext -o Database/Migrations/Postgres -n GenOnlineService.Migrations.Postgres`
- Keep the `-n` argument, otherwise the generated namespace collides with the `Database` namespace used by the data access code and the build fails
- The first `migrations add` for a context writes its model snapshot to a stray `GenOnlineService\GenOnlineService\Migrations\...` folder. Move that file next to the migration (later migrations update it in place) and delete the stray folder
- Check that nothing is missing with `dotnet ef migrations has-pending-model-changes --context <MySqlAppDbContext|PostgresAppDbContext>`
- Commit the generated migration files together with the model change
- Keep schema changes backward compatible: add new columns/tables first and drop old ones in a later release, so an older instance keeps working while a newer one has already migrated

## The migrate command
- `GenOnlineService migrate` uses the configured `db_provider`, lists the applied and pending migrations and asks for confirmation. It does not start the service. Without `--yes` it refuses to run when input is redirected (e.g. in CI)
- After the migrations, every run brings `users.name_key` (the look-alike key of each display name) up to date. When existing names collide under that key and their tag, it keys every other user, leaves the colliding users unkeyed, lists each group of user ids and names and exits with code 2: rename all but one user of each group, then run `migrate` again (`docs/identity.md` section 5a)

# Staff Roles And Bans
Staff roles live in the `user_roles` table and kicks, mutes and bans in the `sanctions` table (a kick is a sanction that ends as it starts). Every grant, revoke, sanction and lift is also written to the append-only `audit_log` table. Rows in both tables carry a `source`: `local` for changes made in this environment, `upstream:<provider>` for rows an upstream sign-in provider manages. Reasons are up to 512 characters. The commands below use the `Database` section, need all migrations applied, and work while the service runs: it applies changes within about 5 seconds without a restart. A role change keeps the player logged in, a ban disconnects them.
- `GenOnlineService roles list [<user_id>]`, `roles grant <user_id> <role> [--reason <text>] [--by <user_id>]`, `roles revoke <user_id> <role> [--reason <text>] [--by <user_id>]`. Roles are `moderator`, `admin` and `streamer`; `admin` has every `moderator` permission and can manage roles. `streamer` is not staff: it carries no permission, no badge and no staff rank (moderators and admins can moderate a streamer like any player), it only switches on client features through `Features:roles`. Removing `streamer` keeps the player logged in, like any role change
- `GenOnlineService bans list <user_id>`, `bans add <user_id> --reason <text> [--days <n>] [--by <user_id>]` (without `--days` the ban is permanent), `bans revoke <user_id> [--reason <text>] [--by <user_id>]` (lifts every active local ban). `bans list` prints every sanction of the user, kicks and mutes included; lifted and expired ones stay in the table as history
- `--by` records which staff account acted, otherwise the log shows `cli`
- Reports and direct messages: reports of messages and of players live in `player_reports` (`open`, `actioned` or `dismissed`). Staff read chat only through a report or an audited lookup, and every read is written to `audit_log`. `GenOnlineService reports list` (open reports), `reports show <report_id> --by <user_id>` (the stored evidence: for a message report the message, up to 10 before and up to 10 after it, and until the retention purge freezes the later messages it also prints them live, marked not yet frozen; for a player report up to 10 of the player's recent messages the reporter could see), `reports close <report_id> [--status actioned|dismissed] [--reason <text>] [--by <user_id>]` (default `dismissed`, the reason is the resolution note), `messages show <message_id> --reason <text> --by <user_id>` (audited lookup of one message, the reason and the staff account are required; `--by` must name an existing user in both `show` commands), `messages purge` (runs the 30 day chat retention purge now, the service also runs it hourly). Moderators and admins hold `chat.delete_any` for `DELETE /api/v1/messages/:id`, and `chat.message_anyone` to send a direct message to any user (friend or not, blocks do not stop it); each such message to a user who is not a mutual friend writes a `staff_message` row to `audit_log` with the message id, never the text, and the user may answer while the conversation holds a stored message from that staff member
- Connection reports: clients send the final result of each connection attempt to a peer with `POST /api/v1/lobbies/:id/connection_reports` (lobby members only), which replaces the legacy `ConnectionOutcome` route (`env/{environment}/contract/{contract_version}/ConnectionOutcome`, removed). The caller must be a member of that lobby (`lobby.not_member`, checked before the body) and `target_user_id` must be another player who is or was a member of it. Rows live in `connection_reports`, one per reporter, lobby, target and attempt (a repeat replaces it), never with an IP address, and are purged 30 days after their last update together with the chat purge (`messages purge` prints the count). Staff read them with `GenOnlineService connections player <user_id> --reason <text> --by <user_id>` (reports the player sent or is the target of, newest first) and `connections lobby <lobby_id> --reason <text> --by <user_id>` (grouped by pair so both sides line up); both print reporter, target, attempt, outcome, transport, IP version, the event timeline and `updated_at`, and write a `connection_lookup` row to `audit_log` before printing. Account deletion removes the reports the user sent or is named in. Privacy: the privacy policy must name these reports, their purpose (troubleshooting a player's connections and lining up both sides of a pair) and the 30 day retention. The metric `genonline.connection.outcomes` counts them by `outcome`, `transport` and `ip_version`
- Player REST endpoints (section 10 of `docs/realtime-protocol.md`, bodies in `docs/api-fixtures/`) take the same access token as the realtime hub and push their effects through it: friends and blocks under `/api/v1/me/friends`, `/api/v1/me/friend_requests` and `/api/v1/me/blocks`, group chats under `/api/v1/groups` (`DELETE /api/v1/groups/:id/members/:user_id` with your own id leaves), `PATCH /api/v1/me` for the display name, `PUT /api/v1/matches/:id/results/me` (idempotent, the stored match roster decides who may report, so it also works after the realtime connection closed, until 24 hours after the match finished) and `GET /api/v1/matchmaking/playlists` (with an `ETag`) and `POST /api/v1/lobbies/:id/connection_reports` (members of that live lobby, `204`). Staff use `POST` and `GET /api/v1/players/:id/sanctions` (kick, mute, ban) and `DELETE /api/v1/sanctions/:id` with the same permissions and rank rule as before; a kick is stored as a `kick` sanction before it is applied and kept only when the target was online, so the sanction, its `audit_log` row and the kick always agree; it never counts as active. `POST /api/v1/reports` reports a message or a player (one open player report per reporter and player). The staff queue is `GET /api/v1/reports?status=open|actioned|dismissed|all` (default `open`, without evidence) and `PATCH /api/v1/reports/:id` with `{status: "actioned"|"dismissed", resolution_note?}`, both `moderation.kick` or higher; resolving writes a `report_close` row to `audit_log`, and a report resolved before stays as it is. Failures are `{"error": "<code>", "params": {...}}` with the HTTP status of section 7; a token without a player session (no `game` scope, an app client, a `gopat-` token) gets `403 {"error":"forbidden","params":{}}` (a failed `perm:<name>` policy names it in `params.permission`) and a missing or refused token `401 {"error":"unauthorized","params":{}}`. Lobby lists, joins and matchmaking pair only the same build: the `game` of the client registry row (`zerohour` or `generals`), the exe and INI CRC and the anticheat
- `Realtime:history_size` (default 50, at most 100) is the number of channel messages replayed in `ChannelHistory` on join and reconnect
- `Features:roles` maps a role to the client features it switches on, for example `"streamer": ["stats_exporter", "observer"]` (without a `Features:roles` section the built-in default gives `streamer`, `moderator` and `admin` both; an environment that sets the section replaces that map entirely, which is why `appsettings.json` carries none). A player's `Ready.features` is the sorted union over their roles, and a role change sends `FeaturesUpdate` with the new list to each of the player's connections within the role reload (about 5 seconds). The known features are `stats_exporter` and `observer`; any other name stops the service at start, a role the service does not know is ignored with a warning. No feature gates anything in the service yet and `streamer` is a placeholder role. Taking the observer seat in a lobby (side `-2`, with `UpdateMySlot`, a host's `UpdateSlots` or a remembered favorite side) works as in the original game: any player may take it when the lobby has `allow_observers`, an AI never, otherwise `invalid_argument {field: side}` (`slots.side` for the host); a remembered favorite falls back to random in a lobby without observers
- `Realtime:group_max_members` (default 10, 2 to 50) is the most members of one group chat, the owner included, sent to clients as `Ready.limits.group_max_members`
- `Realtime:backplane` is `none` (default, one copy needs nothing else) or `redis`, PostgreSQL only (with `Database:db_provider` `mysql` or `mariadb` the service refuses to start with `redis`: those providers run one copy), which needs `Realtime:redis` (a StackExchange.Redis connection string, the service refuses to start without it) and takes an optional `Realtime:redis_channel_prefix` so environments sharing one Redis never mix. Redis carries hub messages and close requests (kicks, bans, revocations) between copies; running two copies also needs sticky sessions and is not supported yet because lobby, matchmaking and session state stay per copy, see `docs/realtime-scaling.md`
- `Realtime:failover:enabled` (default `false`) runs the copy as active or hot standby (`docs/realtime-failover.md`). More than one copy (the Redis backplane, failover and handover) is supported on PostgreSQL only: with `Database:db_provider` `mysql` or `mariadb` the service refuses to start when this is `true`, and `realtime status` and `realtime handover` refuse to run. The copies share the `realtime_lease` row: the active copy renews it every `renew_interval_ms` (500) for `lease_ms` (2500), a standby takes it after the expiry with the next epoch, and a copy that cannot renew by its own deadline (checked apart from the renewal, which is cancelled at that deadline) or sees a newer epoch closes every connection with `server.restarting`; until then a fenced copy closes any connection that calls a hub method or opens, with the same code. `/-/readiness` answers ready only on the lease holder; a standby answers it, the hub upgrade and every `/api` call with `503 {"error":"service.unavailable","params":{"what":"standby"}}` and `Retry-After: 1`. On the shutdown signal, or on `GenOnlineService realtime handover`, the active copy names a live standby as handover target and keeps renewing the lease; once the target confirmed and serves, it waits `switch_delay_ms` (1000, one proxy health check), reports not ready, moves the queue and the lobbies (with the Redis backplane, see `docs/realtime-scaling.md`), then sends `ServerSwitching {retry_after_ms}` (250 to 1000 ms) and closes with `server.switching`, `batch_percent` (5) of its connections every `batch_interval_ms` (200), all of them once `handover_limit_s` (120) has passed, hands the lease to the target (epoch plus one) and stops. A target that does not confirm within one lease period, or whose standby entry lapses during the handover, cancels it: the copy keeps the lease with the next epoch, takes back what the target owned, reports ready again and keeps its open connections, and `realtime handover` then exits with 1. A shutdown signal during an operator handover waits for it. Without a live standby a shutdown closes every connection with `server.restarting` and releases the lease. `GenOnlineService realtime status` prints the holder, epoch, expiry and standby. The shutdown timeout grows to the handover budget plus 10 seconds (`handover_limit_s` plus three lease periods, the switch delay, ten lease periods for the queue move and the forced lobby moves at the limit, and 5 seconds, 168.5 seconds with the defaults), so `terminationGracePeriodSeconds` must cover it. Each process logs its copy id (`POD_NAME` or `HOSTNAME` plus a random suffix) at start. Metrics: `genonline.failover.lease.events` (`acquired`, `lost`, `renewed_late`, `handed_over`), `genonline.failover.handover.duration` and `genonline.failover.connections.moved` per batch. With the Redis backplane on as well, the active copy writes lobbies and the matchmaking queue to Redis and the standby follows them (`Realtime:failover:live_state`: `refresh_ms` 2000, `stream_max_length` 10000, `poll_interval_ms` 100, `rewrite_ms` 0); every write compares the stored owner epoch, so a copy that lost an entity to another copy drops it; a standby announces itself only while it is in sync, so a handover needs an in-sync standby, and a copy that takes over after an unplanned failure restores the lobbies and queue tickets for the players who reconnect, see `docs/realtime-scaling.md`. When both members of a lobby pair come back from the same handover, their pair gets one `StartSignalling` restart once both `SetPeerTransports` arrived, or after `Realtime:failover:handover_signalling_grace_ms` (2000) when one of them is late
- Lobby ids start at 1 and are never reused across restarts or copies: each copy reserves blocks of 100 from the `lobby_ids` counter row (see `docs/schema.md`), and the ids left in a block at shutdown are skipped
- Schema v1 has no `users.admin` or `users.banned`: the import lists old staff to grant again with `roles grant`, and turns legacy bans into `ban` sanctions
- The Discord bot uses slash commands only and requests no privileged intent. Set `Discord:discord_guild_id` so it registers them on start. `/players` and `/lobbies` are public; `/kick`, `/whois`, `/rename`, `/uptime`, `/peak` and `/announce` work only in the admin commands channel. They are allowed when the caller's Discord account is linked (a `discord` row in `identities`) to a GenOnline account with the needed permission (`moderation.kick` for kick and whois, `moderation.rename` for rename, `server.stats` and `announcements.send` for the admin commands), or when the Discord user is listed in `Discord:discord_admins`, which is kept until staff accounts are linked. `/announce` checks the text like `POST /api/v1/announcements` (1 to 512 characters after trimming) and writes an `announcement` audit event with source `discord` before it broadcasts

# Sign-In And Sessions
Every environment is its own identity provider (design: `docs/identity.md`): the `Accounts` section runs ASP.NET Core Identity and an OpenIddict server in this process (`Accounts:enabled`), over the `users` and `identities` tables. With `Accounts:enabled` false the service only validates access tokens of the accounts instance named in `Accounts:issuer`.
- Upstream sign-in: each entry in `Accounts:providers` is a sign-in provider; its redirect URI is `<service>/users/auth/<name>/callback`. Its `kind` is `discord`, `google`, `steam`, `gamereplays` or `oidc`, and defaults to the entry's name when that names a kind (else `oidc`). Keep the names `discord`, `google`, `steam` and `gamereplays`: imported identities are stored under them. `oidc` needs `issuer` (and `client_id`, `client_secret`); `discord` and `google` need `client_id` and `client_secret` (OpenIddict's web providers); `gamereplays` needs those plus `base_url`, the folder of `authorize.php`, `token.php` and `resource.php` (`https://www.gamereplays.org/community/modules/oauth`, scope `user_profile`); any provider but `steam` may set `redirect_uri` when the return URL registered at the provider is another host's, which must redirect the browser, query intact, to the callback; `steam` (OpenID 2.0) needs nothing, and an optional Steam Web API key in `application_key` fills in the persona name. # Account Mail
The `Mail` section sends account mail (email confirmation and password reset links). It is off by default; without it, nothing is sent, addresses stay unconfirmed, nobody waits for a confirmation and only an operator resets passwords (`users password-reset`).
- `Mail:delivery_method`: `none` (default), `smtp`, `brevo`, `resend`, `mailgun` or `cloudflare`. Only the subsection of the chosen method is read. A misconfigured method stops the start with a message naming the key; API keys and passwords are never logged
- `Accounts:issuer` (required unless `none`): the public address of the sign-in pages, for example `https://login.generals.online/`. Every link in account mail is built on it, never on the request's `Host` header (which any client can set), so the service refuses to start with mail and without it. It is also the token issuer (section Sign-In And Sessions)
- `Mail:from` (required unless `none`): the sending address. `Mail:from_name` (default `Generals Online`), `Mail:reply_to` (optional address), `Mail:timeout_seconds` (1 to 120, default 15)
- `smtp` (MailKit): `Mail:smtp:host` (required), `Mail:smtp:security` `starttls` (default), `tls` or `none` (a relay on the same host or network only), `Mail:smtp:port` (default 587, or 465 with `tls`), `Mail:smtp:user` and `Mail:smtp:password` (both or neither)
- `brevo`: `Mail:brevo:api_key`. `resend`: `Mail:resend:api_key`. `mailgun`: `Mail:mailgun:api_key`, `Mail:mailgun:domain` (the sending domain) and `Mail:mailgun:region` `us` (default) or `eu`. `cloudflare` (Cloudflare Email Service, beta): `Mail:cloudflare:api_token` (a token allowed to send) and `Mail:cloudflare:account_id`
- Example (Brevo): `Accounts__issuer=https://login.generals.online/`, `Mail__delivery_method=brevo`, `Mail__from=no-reply@generals.online`, `Mail__from_name=Generals Online`, `Mail__brevo__api_key` from the secret store
- Mails are MJML templates compiled in the service (`GenOnlineService/Mail/Templates`), each with a plain-text part; their links point at `Accounts:issuer`. The name in a mail is the player's Name#tag, or the address while a name is still owed
- `GenOnlineService mail test <email address>` sends one test mail through the configured method and prints whether the provider accepted it: exit 0 sent, 1 not configured or refused (the reason printed), 2 a bad command line

# API Tokens
Machines (website backend, Discord bot, partners, monitoring) call the API with `Authorization: Bearer gopat-<40 characters>`, the only machine credential (design: `docs/api-tokens.md`). A token belongs to a service account or to a staff user, carries explicit scopes and always expires. Each request gets the token scopes the owner still holds (service account grants, or the user's staff roles), so removing a grant, a role or a token narrows access within about 5 seconds. Every refused token gets the same `401` body; the reason is logged with the token id and counted in `genonline.api_token.auth_failures`. Only the SHA-256 of a token is stored, the token itself is printed once.
- `GenOnlineService service-accounts list`, `service-accounts create <name> [--description <text>]`, `service-accounts grant <name> <permission>`, `service-accounts revoke-grant <name> <permission>`, `service-accounts disable <name>`, `service-accounts enable <name>`
- `GenOnlineService tokens list [--owner service:<name>|user:<id>] [--all true]`, `tokens create --owner service:<name>|user:<id> --name <name> --scopes <p1,p2> --expires <yyyy-mm-dd> [--allowed-ips <cidr,cidr>]`, `tokens rotate <id> [--overlap-minutes <0-1440>] [--expires <yyyy-mm-dd>]`, `tokens revoke <id> [--reason <text>]`
- Machine permissions (`users.revoke`, `ops.database`, `match_history.read`, `lobbies.read`) are held only by service accounts. The privileged ones (`users.revoke`, `ops.database`) can only be granted and minted here on the host, and their tokens need `--allowed-ips` and live at most `ApiTokens:privileged_max_lifetime_days` (30). Other tokens live at most `ApiTokens:max_lifetime_days` (365); an owner has at most `ApiTokens:max_active_per_owner` (20) active tokens
- Rotation stops the old token at once unless `--overlap-minutes` keeps it working for a planned switch. Every mint, rotate, revoke and grant is written to `audit_log`, never the token
- Staff with `tokens.manage` manage partner service accounts and their tokens on the staff pages (`/admin/partners`) too, with the same rules: no privileged permission is granted or minted there
- `genonline.api_token.expires_in{token_id,name,owner}` reports the seconds left per active token (alert at 14 and 3 days); the service also logs a daily warning for tokens inside `ApiTokens:expiry_warning_days`. Revoked and expired rows are deleted after `ApiTokens:retention_days` (90)
- `allowed_ips` needs the real client address: set `TrustedProxies` when the service runs behind a proxy

# API Docs
Interactive docs of the REST API are at `/api/docs`, and `/api` leads there (Scalar, its page and script served by this service, nothing from a CDN): every `/api/v1` route with its summary, body, answers and errors, how it authenticates and the permission it needs, and a "try it" that sends the call from the page with a pasted access token or `gopat-` token. The OpenAPI 3 document behind it is `/api/openapi/v1.json` (also `/api/openapi/v1.yaml`), generated from the controllers on each request with the request's own base URL.
- Both are read-only metadata: they need no sign-in, and a call made from the page passes the same authentication and permission checks as any other call. The realtime hub is not in them (`docs/realtime-protocol.md`)
- `OpenApi:enabled` (default `true`) turns both off; they then answer 404
- A proxy in front must pass `/api` itself, `/api/docs` and `/api/openapi` for them to be public (the outpost-infra route allowlist); without that they answer only on the service itself
- `docs/api.md` stays the reference for the rules behind each route; the document is generated from the code and its attributes (`GenOnlineService/OpenApi`), and `ApiDocsTests` fails for an `/api/v1` route without a summary, a request or answer schema or a security requirement

# Observability

The service can export OpenTelemetry logs, metrics, and traces over OTLP, with Sentry as an optional destination for errors, logs, and traces. See [docs/observability.md](docs/observability.md) for configuration, coverage, metric names, privacy controls, and an Alloy example.

Finished matches are published to the external leaderboards (GameReplays' Strata), and ratings are read back from them, when the `ExternalLeaderboards` section sets `PostUrl`, `PostToken`, `GetUrl` (with `{playerId}`) and `GetToken`. Without the section the service publishes nothing, queues nothing to publish later, takes ratings from the stored values, and logs one warning at startup; a section that is present but incomplete is an error.
