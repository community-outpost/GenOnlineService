# Running more than one realtime copy

The realtime hub (`/realtime`, see `realtime-protocol.md`) is built so an environment can later run more than one service copy, for deploys without downtime. Today one copy per environment is the supported setup.

## PostgreSQL only

Every multi copy feature (the Redis backplane, failover and handover) needs `Database:db_provider` `postgres`. With `mysql` or `mariadb` the service runs one copy: it refuses to start with `Realtime:backplane` `redis` or `Realtime:failover:enabled` `true`, and the error names the setting and PostgreSQL.

## One copy

Nothing extra. `Realtime:backplane` defaults to `none`: hub messages and close requests stay inside the process.

## What the code already does for several copies

- Every server event is addressed through SignalR groups, never through a connection id the service looked up: `user:<id>` (every connection of the user), `user:<id>:game`, `user:<id>:launcher`, `user:<id>:chat` (the one connection of that session type), `channel:<id>`, `lobby:<id>`. With a backplane these reach connections on every copy.
- SignalR users are named by the user id in the session principal (`RealtimeUserIdProvider`, the OpenIddict subject). Server events still go through `user:<id>`, which a connection joins just before `Ready`, so `Ready` stays the first event.
- Kicks, bans and revocations are close requests (`RealtimeControl.RequestClose`). The copy that issues one closes its own matching sessions first, then publishes it; every other copy closes only its own matching sessions with the same close record (`moderation.kicked` or `moderation.banned` after the `ModerationNotice`, `auth.revoked`). A sign-in revocation closes only the connections of that sign-in on every copy.
- A kick of a user this copy does not hold waits up to 2 seconds for another copy to confirm it closed a session, otherwise it answers `moderation.target_offline` as before.
- Lobby ids come from the `lobby_ids` counter row in the database. Each copy reserves a block of 100 ids with one atomic update and reserves the next block in the background when 20 are left, so no restart and no other copy ever hands out the same lobby id again. The ids left in a block when a copy stops are skipped. A database outage fails only the `CreateLobby` that needs a new block.

## Active and standby copies

`Realtime:failover:enabled` (default `false`) runs two copies as active and hot standby, see `realtime-failover.md`. Running more than one copy is supported on PostgreSQL only. Only the copy that holds the `realtime_lease` row serves players, and the target of a running planned handover next to it: `/-/readiness` is ready only there, and a standby refuses the hub upgrade and `/api` calls with a retryable 503. A planned handover (`GenOnlineService realtime handover` or the shutdown signal) needs a live standby entry. The holder keeps the lease and renews it for the whole handover: it names the standby as `handover_target`, the target confirms (`handover_confirmed_at`) and serves, then the holder reports not ready, moves the live state (below), sends every remaining connection `ServerSwitching` and closes it with `server.switching` in batches, and only when it holds no connection and owns nothing hands the lease to the target with the epoch plus one and exits. A target that does not confirm within one lease period, or whose standby entry lapses during the handover, cancels it: the holder keeps the lease with the epoch plus one, takes back what the target owned and reports ready again; the target sees the cancel and closes its connections with `server.restarting`. A holder that dies during the handover lets its lease expire, and the target takes it as after any failure. During the handover the holder refuses `CreateLobby` and `JoinQueue` with `service.unavailable {what: standby}` and switches the caller to the target. Without the Redis backplane, lobbies and the queue end on the old copy as on a restart. Both copies need the same `Accounts` issuer and certificates.

With failover and the Redis backplane both on, the copies keep the live state in Redis (build steps 3 and 4): each lobby (settings, slots, members and former members, host, state, countdown deadline, match id and start data, mesh check bookkeeping, the pairs that reported connected and each pair's connection order) and the matchmaking queue (tickets, buckets with their widening, matched setups in progress) as a versioned JSON document in the hash `genonline:live:state`, its owner copy and owner epoch in `genonline:live:epochs`, each accepted change as an entry in the capped stream `genonline:live:stream` (`XADD MAXLEN ~` `Realtime:failover:live_state:stream_max_length`, 10000) and each copy's count of accepted writes in `genonline:live:seqs`, all behind `Realtime:redis_channel_prefix` and a colon when it is set. Lobby chat stays in the database. The documents hold lobby passwords, the host coordinates the latency estimates need and the match start data, so Redis is trusted like the service process. Every stored document carries `v` (1), the owner copy, the owner epoch, the copy that wrote it and a version per entity that counts from 1 under each owner; formats change additively only, readers ignore unknown fields, and an unreadable document is skipped and counted. Every write is one Lua script that compares the stored owner epoch: only the owner writes an entity at the epoch it holds, a new lobby starts at epoch 1, and a deleted entity keeps a marker for ten minutes, during which nothing writes it again. A refused write means another copy owns the entity now: the copy drops it, without finishing it, and closes the connections of its members with `server.switching`. A copy that takes the lease claims every entity another copy owned with the owner epoch plus one; a fenced copy drops every lobby and its queue without finishing them. Writes are queued and sent pipelined from their own loop, never on a player's command path and never under the lobby gate, so changes not yet in Redis are lost on a failure; a failed batch sends its deletes again and every entity is written again. `rewrite_ms` (0, off) writes unchanged entities again that often when set. A standby, and a handover target, loads every document, then follows the stream every `poll_interval_ms` (100) into an in-memory mirror without running lobby logic; a missing write count of a copy (the stream was trimmed past it) makes it reload everything. It is in sync once it applied the stream up to the latest entry and read it within one lease period, and it announces itself as standby only while in sync, so a planned handover needs an in-sync standby. In a planned handover the queue moves first: the holder stops forming matches, writes the queue with the target as owner at the owner epoch plus one, waits until the target wrote it under its own name, then switches its queued players, whose tickets wait on the target; a quick match setup already locked finishes on the holder. Then each lobby moves when quiet (setup with no countdown, mesh check or start in progress, or in game), all at once after `handover_limit_s`: the holder writes its final state with the target as owner, the target takes it from its mirror and writes it under its own name, and only then the holder sends `ServerSwitching` to that lobby's members and closes them with `server.switching`, so a lobby's members always move together. From its final capture on a moving lobby is frozen: its tick stops, and a change to it or a join is refused with `service.unavailable {what: standby}` until it moved or the move was cancelled, which resumes its countdown from the same deadline. After the limit the remaining lobbies move eight at a time. A player queued on the holder after the queue left (a requeue of a failed setup, or a raced `JoinQueue`) follows with a ticket of its own (`ticket:<user_id>`), handed to the target the same way. Members of a lobby the target kept and queued players keep their relay credentials when they switch, also inside their reconnect grace without a connection; those with an open connection show friends no presence change, and the target publishes them offline when their seat or ticket ends unclaimed. Members of a lobby the target did not keep, and players switched because another copy took their lobby, end as usual. While a lobby moves, a kick, ban, logout, supersede or grace expiry of a member leaves the frozen lobby as it is and reaches the target as a note (`leave:<lobby_id>:<user_id>`), which removes the seat there; if the move is cancelled the holder applies those leaves itself and deletes the notes. A quick match bucket of a moving lobby is frozen too: its start or abort holds the lobby under its gate, so a forced move waits for it or freezes it, and the bucket ends without a requeue once the lobby left. Players switched because another copy took their lobby keep their relay credentials. Players in the batches switch as in build step 1. A fenced copy closing its sessions deletes no relay credentials and publishes no presence, the copy that serves now does; a player on a cut off but alive copy who never reconnects therefore stays online for friends who did not reconnect since, exactly as after a crash of that copy, and a late offline never overwrites an online status on the copy that serves. A standby that takes the expired lease of a holder it watched (an unplanned failure, not the first take of a cold start) turns the mirror into live lobbies and tickets before it reports ready, but only when the mirror was in sync within two lease periods (otherwise it logs a warning, counts `restore_skipped_stale` and starts empty as a cold start does); a user stored in two lobbies keeps the seat of the more recently written one, and unclaimed restored tickets stay in the written queue during the grace: a countdown continues to its stored deadline, a start still in its mesh check goes back to setup, pending mesh checks and probes are dropped and new ids start at a time based value, and finished lobbies and quick match setups not yet in game stay out (their players get their tickets back with `MatchRequeue setup_failed`). A moved, restored or taken back lobby replaces a stale local copy of the same lobby, whose connected members keep their seats. A reconnecting member takes its seat again and gets `LobbyState`, the lobby chat as `ChannelHistory` and `StartSignalling` for each pair that has not reported connected; a queued player gets `MatchmakingStatus matchmaking.queued` and keeps the queue time. Members and tickets not reclaimed within `Core:reconnect_grace_period_ms` are dropped. Presence needs nothing of this: every player reconnects to the copy that serves, which publishes presence on each connection as a single copy does. Metrics: `genonline.failover.live_state.events` (`loaded`, `stream_gap`, `write_failed`, `write_refused`, `queue_lost`, `restore_skipped_stale`), `genonline.failover.mirror.lag`, `genonline.failover.lobbies.restored`, `genonline.failover.lobbies.lost`, `genonline.failover.lobbies.moved`, `genonline.failover.handover.duration`, `genonline.failover.connections.moved` per batch and `genonline.failover.lease.events` (`acquired`, `lost`, `renewed_late`, `target`, `target_stepped_down`, `handed_over`, `handover_cancelled`).

## The Redis backplane

| Key | Meaning |
|---|---|
| `Realtime:backplane` | `none` (default) or `redis`; `redis` needs PostgreSQL |
| `Realtime:redis` | StackExchange.Redis connection string, required with `redis`; the service refuses to start without it or when Redis cannot be reached |
| `Realtime:redis_channel_prefix` | optional prefix of every Redis channel, so environments sharing one Redis never mix |

Redis is the documented option because `Microsoft.AspNetCore.SignalR.StackExchangeRedis` is the only backplane Microsoft maintains. It is used with PostgreSQL only, see above. The community Postgres backplanes are deferred until they mature. One Redis connection per copy carries the SignalR backplane, the chat fan-out (`realtime.chat`, see below), the block changes (`realtime.blocks`, see below) and the close requests (`realtime.close`, `realtime.close.ack`). Redis pub/sub is not durable: a close request published while Redis is down is lost (the copy that handles the kick or revocation still closes its own connections), and a publish during an outage can stall that call until the StackExchange.Redis timeout (5 s by default) before it fails.

## Why two copies are not supported yet

Two copies need Redis, the same `Accounts:issuer` and the same `Accounts` signing and encryption certificates on both (so a token one copy issued is valid on the other), and sticky sessions in Envoy (hash on a cookie or the source address). The hub is websockets only, so a connection stays on its copy anyway; stickiness matters for reconnects and for the HTTP session calls that go with them.

Even then, this state is still kept per copy in memory and is not shared:

- sessions, reconnect grace and session takeover (`session.superseded` only happens when both connections reach the same copy)
- lobbies, the lobby list and matchmaking, including the connection order of each pair of lobby members (attempt and step, section 6.6 of `realtime-protocol.md`)
- the transports each session sent with `SetPeerTransports`: a lobby reads them from the member sessions on its own copy, and a pair whose member session is on another copy gets `StartSignalling` without the four connection order fields
- channel membership lists (`ChannelMembers`), presence of users on other copies, name change audiences beyond the user and their friends
- the cached friend lists and friend requests of online users that the friends-only lobby check and the lobby list read: they are loaded when a session starts and updated only by friend changes made through the same copy (a block ends them on every copy, see below)
- game session registrations, the chat rate limit and the report rate limit

Moving that state to a shared store is later work. Until then two copies are not supported.

## What the backplane covers

Covered: every event sent to a user, a session type of a user, a channel or a lobby group, `All` notices, close requests with their notice and close record, and block changes.

Not covered: anything decided from the per copy state above, for example whether a user is online or who is in a lobby.

## Block filter of channel and lobby chat

With `none` the copy that sends leaves blocked users out by connection id, as before. With `redis` a channel or lobby `MessageCreate` does not go through a SignalR group send. The sending copy reads the users blocked either way with the author from the database, so a block or unblock made through any copy counts from the next message on, and publishes the message with those user ids on `realtime.chat`. Every copy, the sender included, takes the messages from that channel one at a time in publish order and queues each for its own connections in the channel or lobby group, except those users. Each connection has its own ordered queue of chat writes, so a client that stops reading holds up only itself; a connection with more than 256 chat messages waiting is aborted, and the client reconnects and reads the history. A copy knows its own group members because it mirrors the group calls of its own connections. The messages of a channel therefore keep one order on every copy; the order against other events of that channel (`MemberAdd`, `MemberRemove`, `MessageDelete`), which travel on the SignalR backplane channels, is not guaranteed across copies. Direct and group messages go to user groups after a check against the database and are unchanged.

## Blocks outside chat

Each copy keeps the block list of every user online on it, loaded when the session starts. A block or unblock (`PUT` and `DELETE /api/v1/me/blocks/:user_id`, and the block a friend request lifts) is written to the database first and then applied to the lists of this copy. With `redis` the copy also publishes `{"user_id", "other_id", "blocked"}` on `realtime.blocks`. Every copy, the sender included, takes these one at a time in publish order, applies the change to the lists of both users (a block also ends their friendship and pending requests there) and then reads the blocker's list again from the database, so the last stored change wins in whatever order the messages arrive. A change that arrives while a session loads its lists makes that session read its block list once more. No path deletes users or blocks outside these endpoints, and the CLI changes no blocks.

Checks that run for many lobbies or tickets at once read the lists: the lobby list filter (`WatchLobbyList`, the list updates and `GET /api/v1/lobbies`) and the matchmaking pairing of tickets and buckets. Rare decisions also read the database when they are made, so a lost message never lets a blocked player through. `JoinLobby` reads which members blocked the joiner and answers `lobby.blocked` when the host did, at the same place in the order of checks as before. A quick match reads every block among its players before it forms; when one exists it drops the setup with `MatchRequeue setup_failed` and reloads the blockers' lists, so the same pairing does not form again. The social endpoints (friend requests, block and unblock) read blocks from the database. A decision whose database answer contradicts a list reloads that list. As with one copy, a lobby a watcher already sees leaves that watcher's list at the lobby's next update, not at the block. With `none` nothing is published, the lists stay exact as before and the database reads give the same answers.

Redis pub/sub is not durable: a change lost while Redis is down leaves another copy's list stale until the next change of that user, a join or quick match that reads the database, or a reconnect. Until then the lobby list on that copy may still show a lobby whose host blocked the viewer, or hide one after an unblock. During a mixed-version rollout the old copies do not read `realtime.blocks`.
