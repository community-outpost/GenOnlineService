# REST API v1

Every REST route of the service. The realtime hub is `/realtime` (`docs/realtime-protocol.md`); the routes of its section 10 (social, groups, sanctions, messages, reports, `PATCH /me`, match results, playlists, connection reports) are listed there and not repeated here.

## Conventions

- Base path `/api/v1`; operator probes and checks under `/-/`; standards under `/.well-known/`. There is no other route prefix.
- `Authorization: Bearer <access token or gopat- token>`. "Session" below means an OpenIddict access token of a registered client; "game session" means one with the `game` scope and a `POST /api/v1/auth/session` registration; "web session" means a token of an `app` client.
- The sign-in cookie, GitLab style (T16): the routes marked "cookie" below (and the section 10 routes listed under [Staff pages](#staff-pages-admin)) also accept the website sign-in cookie of the environment's own sign-in pages (`go_session`), so the staff pages call `/api/v1` directly. Any `Authorization` header keeps the bearer path, and every other route answers a cookie alone with 401 `unauthorized` as before. A cookie request that changes something (`POST`, `PATCH`, `PUT`, `DELETE`) must carry the antiforgery token of the signed-in user in the `RequestVerificationToken` header (the staff pages read it from the `csrf-token` meta tag of their host page), or gets 400 `csrf`. A cookie request with an `Origin` header other than this host's own origin gets 403 `forbidden`, whatever `AllowedOrigins` (CORS) allows, so CORS never lends the cookie to another site. A staff account with a password and no second factor gets 403 `two_factor_required` on every cookie request. The permission, rank and audit rules are those of a bearer caller; the audit source of a cookie action is `api`. Bearer requests need no header and are unchanged.
- JSON is snake_case, timestamps are ISO 8601 UTC with whole seconds, absent values are `null`.
- Every failure is `{"error": "<code>", "params": {...}}` with the codes of section 7 of `docs/realtime-protocol.md`: 400 `invalid_argument {field}`, 401 `unauthorized`, 403 `forbidden {permission}` (or `{}` when no single permission applies), 404 `not_found {what}`, 409 conflicts, 422 other rule failures, 503 `service.unavailable {what}`. An unknown `/api` or `/-/` path answers 404 `not_found {what: "route"}`, a known path with another method 405 `method_not_allowed`.
- Offset pages: `?page=&per_page=` (default 20, at most 100) with `X-Total`, `X-Page`, `X-Per-Page`, `X-Next-Page` and `Link rel="next"`. Keyset pages (matches, audit events): `after_id` and a `Link rel="next"` when the page is full.
- Example bodies: `docs/api-fixtures/`, one file per request and response type, checked by `ApiFixtureTests`.
- Interactive docs: `/api/docs` on each environment (`/api` leads there), built on the OpenAPI 3 document `/api/openapi/v1.json` (also `.yaml`) that the service generates from its controllers; no sign-in, a call from the page is checked like any other. `OpenApi:enabled` (default `true`) turns both off, and a proxy in front must pass `/api`, `/api/docs` and `/api/openapi` (the outpost-infra route allowlist). This file stays the reference for the rules; the generated document carries the shapes.

## The caller

| Route | Auth | Answer and errors |
|---|---|---|
| `GET /api/v1/me` | session of any client, the website included | `{user_id, display_name, tag, roles, permissions}` |
| `GET /api/v1/me/sessions` | session of any client | `{sessions: [{type: game\|launcher\|chat, client_id, registered_at}]}` |
| `POST /api/v1/me/linked_accounts/:provider/sign_in_token` | game session | `{token, expires_in}`; for `eos` the EOS ID token. `not_found {what: provider}` (404), `session.game_required` (403), `service.unavailable {what: linked_account, provider}` (503) |
| `PUT /api/v1/me/linked_accounts/:provider` | game session | body `{proof}` (for `eos` the Epic Connect ID token), 204; `not_found {what: provider}` (404), `invalid_argument {field: proof}` (400), `session.game_required` (403), `linked_account.invalid_proof` (422), `linked_account.mismatch` (403), `linked_account.in_use` (409), `linked_account.locked` (409), all four with `{provider}`, `service.unavailable {what: linked_account, provider}` (503) |

Account deletion (`DELETE /api/v1/me`) is not built: it needs a data-retention decision. Signing out is `DELETE /api/v1/auth/session`.

## Tokens and service accounts

The management routes need a web session (never a game session or a `gopat-` token): the bearer session of a registered `app` client, or on the routes marked "cookie" the staff pages' sign-in cookie. See `docs/api-tokens.md` for the rules.

|---|---|---|

## Administration

| Route | Permission | Answer |
|---|---|---|
| `GET /api/v1/players/:id/roles`, `PUT` `{roles}`, `DELETE` | `roles.manage` | `{roles}`; PUT and DELETE change the locally granted roles, roles from the sign-in provider stay; the roles that change follow the rank rule below (a request that changes nothing answers as before) |
| `PUT /api/v1/players/:id/roles/:role`, `DELETE` | `roles.manage`; cookie | one local role: PUT grants it (200 `{roles}`, also when held already, which changes nothing), DELETE revokes it (204); an unknown role `invalid_argument {field: role}`; a role held only through a sign-in provider 409 `roles.upstream {role, source}`, it follows that provider's sign-ins; a role not held `not_found {what: role}`. Each change writes a `role_grant` or `role_revoke` audit row `{role, source: local}` and reloads the role cache, so it applies at once. Rank rule (`owner` 3, `admin` 2, `moderator` 1, any other role 0, `streamer` included): the caller outranks the player (`moderation.target_outranks`, 403; never themself, `invalid_argument {field: id}`) and the role ranks strictly below the caller's highest role (403 `roles.rank {role}`); a service account token acts with admin rank, as for staff renames. So an owner manages `admin`, `moderator` and `streamer` of everyone below owner; an admin manages `moderator` and `streamer` of players and moderators. `roles.rank` answers an admin or a service account granting or revoking `admin` or `owner`, and anyone granting or revoking `owner`: `owner` is granted with the `roles` CLI only, and never by a sign-in provider |
| `GET /api/v1/audit_events?actor_id=&target_id=&target_kind=&action=&after_id=&per_page=` | `audit.read`; cookie | `{audit_events}`, newest first, keyset paged; `target_kind` (such as `user`, `token`, `service_account`) narrows `target_id`, which alone matches every kind |
| `GET /api/v1/application/settings`, `PUT` | `settings.manage`; cookie | `{motd}`; PUT is partial, `null` clears a key |
| `GET /api/v1/anticheat_reports/:kind?reviewed=&user_id=` | `anticheat.review`; cookie | `kind` is `new_accounts`, `modules`, `probes`, `devices` or `quickmatch_rules` (`invalid_argument {field: kind}`); `{reports: [{id, kind, player: Member, match_id, module_name?, module_path?, module_size?, reason?, lobby_id?, playlist_id?, method?, sides?, reported_at?, reviewed_at, reviewed_by}]}`, newest first, offset paged; `reviewed` is `false` (default), `true` or `all`; `match_id` is null for a report raised at sign-in and for a `quickmatch_rules` report made before its match started. `quickmatch_rules` lists quick match requests a genuine client never sends (today `UpdateMySlot` and `UpdateSlots` asking for a side other than -1 in a playlist without army selection, refused with `lobby.army_selection_disabled`), kept once per player and lobby with the `lobby_id`, `playlist_id`, hub `method`, requested `sides` (array of ints) and `reported_at` |
| `PATCH /api/v1/anticheat_reports/:kind/:id` | `anticheat.review`; cookie | body `{reviewed: true}`, 204; the row stays and gets `reviewed_at` and `reviewed_by`, an audit row `anticheat_review` is written; a row reviewed before answers 204 and changes nothing |
| `POST /api/v1/announcements` | `announcements.send`; cookie | body `{message}`, answers `{delivered_to}`; connected clients get `Notice` `server.announcement` |
| `POST /api/v1/players/:id/password_reset` | `accounts.support`; cookie only | body `{reason}` (required, `invalid_argument {field: reason}`), answers `{password}`: a new random password of 20 characters, in this answer only, never logged or audited. The same reset as `users password-reset`: the old password stops working, the lockout ends, the security stamp changes so website sign-ins end within a minute, and every sign-in of the account is revoked with its refresh tokens and game sessions, its realtime connections closing with `auth.revoked`, and every personal `gopat-` token it owns is revoked. Follows the staff rank rule (`moderation.target_outranks`, the caller themselves `invalid_argument {field: id}`); an account without an email address signs in with a provider only and answers 422 `account.no_password`; `password_reset` in the audit log with `{sign_ins_revoked, tokens_revoked}` |
| `POST /api/v1/players/:id/two_factor_reset` | `accounts.support`; cookie only | body `{reason}` (required), 204. The same reset as `users two-factor-reset`: two-factor sign-in off, the authenticator key and every recovery code deleted, the password kept, the lockout ended, every sign-in revoked as for a password reset. The rank rule as above; an account without two-factor sign-in answers 422 `account.no_two_factor`; `two_factor_reset` in the audit log with `{sign_ins_revoked, tokens_revoked}` |
| `GET /api/v1/staff/text_rules/terms?query=&language=&category=&severity=` | `textrules.manage`; cookie | `{total, terms: [{id, term, language, category, severity, match, source, updated_by, updated_at}]}` ordered by language and word, at most 1000 (`total` counts every match); `query` matches part of the word |
| `POST /api/v1/staff/text_rules/terms`, `PATCH /api/v1/staff/text_rules/terms/:id`, `DELETE` | `textrules.manage`; cookie | body `{term, language, category, severity, match}` (`language` `en` or `ar`, `category` `slur`, `sexual`, `profanity`, `insult`, `impersonation` or `reserved`, `severity` `block` or `flag`, `match` `word`, `anywhere` or `literal`, the Keycloak plugin's rule); POST answers 201 with the word, PATCH changes the fields sent, DELETE 204. The word is stored trimmed and lower case, at most 64 characters; a bad field `invalid_argument {field}`, a word the language lists already 409 `conflict {what: term}`, an unknown id `not_found {what: term}`. Audited as `text_term_add`, `text_term_update` (`{from, to}`) and `text_term_remove` |
| `GET /api/v1/staff/text_rules/exceptions`, `POST`, `DELETE /api/v1/staff/text_rules/exceptions/:id` | `textrules.manage`; cookie | `{exceptions: [{id, term, language, source, updated_by, updated_at}]}`; POST `{term, language}` 201, DELETE 204; words that stay allowed although they contain a listed word; audited as `text_exception_add` and `text_exception_remove` |
| `GET /api/v1/staff/text_rules/workflows`, `PUT /api/v1/staff/text_rules/workflows/:kind` | `textrules.manage`; cookie | `{workflows: [{kind, definition: {rules: [{name, expression, outcome, enabled}]}, outcomes, fields, updated_by, updated_at}]}` for `display_name`, `lobby_name` and `chat`; PUT takes `{rules}`. An expression reads `input.Kind`, `input.Matches`, `input.Block`, `input.Flag`, `input.Slur`, `input.Sexual`, `input.Profanity`, `input.Insult`, `input.Impersonation` and `input.Reserved` with numbers, strings, comparisons and `&&`, `||`, `!` only; at most 32 rules. | `POST /api/v1/staff/text_rules/test` | `textrules.manage`; cookie | body `{kind, text}` (text 1 to 512 characters), answers `{kind, outcome, rule, masked, readings: [{name, text}], hits: [{term, language, category, severity, match, reading, start, end, text}], facts}`: what the rules of this copy decide, how the text was read (`folded`, `folded_alt` with 1 read as l, `arabizi`) and what it matched; nothing is stored or audited |

Sign-out everywhere for another user is `POST /api/v1/users/:id/revoke_sessions` (`users.revoke`).

The account support routes take over an account, so only the sign-in cookie of the staff pages reaches them: a game session or a token answers 403 whatever permissions it carries. `accounts.support` is the admin's (and the owner's), never a moderator's, and no service account is ever granted it (`forbidden {permission}`).

## Staff pages (`/admin`)

Each environment serves its own staff pages while `Accounts:enabled` (S12): a WebAssembly app under `/admin` (`/admin/reports`, `/admin/players`, `/admin/players/:id`, `/admin/matches`, `/admin/matches/:id`, `/admin/anticheat/:kind`, `/admin/audit`, `/admin/announcements`, `/admin/settings`, `/admin/partners`, `/admin/partners/:id`, `/admin/live`, `/admin/lobbies/:id`; `/admin` is the dashboard). A page without the sign-in cookie redirects to `/users/sign_in?ReturnUrl=`; a signed-in account without `moderation.kick`, `moderation.mute` or `moderation.ban` gets a 403 page; a staff account with a password and no second factor is sent to `/profile/two_factor_auth` first. The page shell loads `/_framework/*` (the WebAssembly files) and `/_content/*`, which `MapStaticAssets` serves.

The host page carries who is signed in and the antiforgery token in meta tags: `go-portal-session` (`{user_id, display_name, tag, roles, permissions, staff}`), `csrf-header` and `csrf-token`. The pages then call `/api/v1` with the cookie (the cookie rule under Conventions): `GET /api/v1/staff/overview`, `GET /api/v1/players/search`, `GET /api/v1/players/:id/staff_view`, `GET /api/v1/players/:id/inspection`, `GET /api/v1/staff/investigate` (`/admin/investigate`, linked from each device fingerprint, address and country of the player page), `GET /api/v1/matches/:id`, `GET /api/v1/matches/search`, `GET` and `PATCH /api/v1/anticheat_reports`, `PUT` and `DELETE /api/v1/players/:id/roles/:role`, `GET /api/v1/audit_events`, `GET /api/v1/staff/lobbies` and `GET /api/v1/staff/realtime` (`/admin/live`, refreshed every 10 seconds until paused), `GET /api/v1/players/:id/connection_reports` (the Connections tab of the player page) and `GET /api/v1/lobbies/:id/connection_reports` (`/admin/lobbies/:id`), the service account routes under [Tokens and service accounts](#tokens-and-service-accounts), `GET` and `PUT /api/v1/application/settings` (the message of the day, `/admin/settings`), `POST /api/v1/players/:id/password_reset` and `POST /api/v1/players/:id/two_factor_reset` (the player page's Account menu, `accounts.support`; the new password shows once with a copy button), `POST /api/v1/announcements` (`/admin/announcements`, which lists the recent ones from `GET /api/v1/audit_events?action=announcement` with `audit.read`), the text rules routes under `/api/v1/staff/text_rules` (`/admin/text-rules`, `textrules.manage`), and of section 10 of `docs/realtime-protocol.md` `GET /api/v1/reports/search`, `PATCH /api/v1/reports/:id`, `PATCH /api/v1/players/:id`, `POST /api/v1/players/:id/reset_name`, `POST /api/v1/players/:id/sanctions`, `DELETE /api/v1/sanctions/:id` and `DELETE /api/v1/messages/:id` (a reported message, from the report queue). Those section 10 routes otherwise need a game session; `GET /api/v1/reports/search?status=&search=&sort=` is the staff queue paged in the database (`status` one or more of `open`, `actioned`, `dismissed` comma separated, or `all`, default `open`; `sort` `asc`, the default, or `desc` by creation; offset paged; `{reports}` as `GET /api/v1/reports`, and a message report also carries `message_content`, the text of the reported message as the report stored it).
